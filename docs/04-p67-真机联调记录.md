# 04 — P67 手环真机联调记录（2026-09-25）

> 环境：server @ 10.10.10.53（网关 10409 / 控制台 8080），agent = Redmi Note 9 Pro（10.10.10.61，agentId `phone-9cec3446b7f123cd`），DUT = Xiaomi Smart Band 10 Pro `2C:0D:CF:72:20:84`（band-2084）。
> 本文记录真机首测的实测结论与避坑点，是 01~03 文档（固件源码静态分析）的**实测校准**。

## 1. 手环端前置条件（最重要）

1. **必须进工厂测试模式**：手环正常界面只发 `connectable=false` 的慢速信标（1 秒一次、无服务 UUID），
   此时 BLE 协议层就无法连接，任何 App 直连都零回调。进 FACTEST 后广播变为
   `connectable=true`，设备名 `P67-FACTEST-2084`，LC 服务才可用。
2. **不能和手机系统蓝牙绑定**：手环一旦和小米穿戴等绑定（DUAL 模式占用经典链路），
   广播行为改变，agent 连不上。联调前在 设置→蓝牙 里取消配对。
3. 文档 03 里"灭屏蓝牙下电"对 FACTEST 驻屏场景不适用，但仍建议保持亮屏。

## 2. LC 通道实测校准（对 01/02 文档的修正）

| 项 | 文档 | 实测 |
|-|-|-|
| 连接 | 直连即可 | ✔ 200ms 内建立 |
| 服务发现 | — | ✔ 约 600ms；**偶发挂死**（见 §4 遗留问题） |
| MTU | 需协商 | ✔ 512 一次成功，与写 AT 无冲突 |
| CCCD | 必须先写 | ✔ status=0 |
| 写 AT | Write No Response | **硬性要求**：带响应写被固件 ATT `0xFC Write Request Rejected` 拒绝。特征 props=0x14（WRITE_NR+NOTIFY），没有 WRITE 属性 |
| AT 回包 | Notify 异步 | ✔ 实测 `00AT^BLUETOOTHLE` → `BLUETOOTHLE=OK`；`00AT^SWVER=APP` → `SWVER=OK,3.101.042monkey`（\r\n 结尾） |
| 电量服务 0x180F | 未编译 | ✔ 确认不在服务表（服务发现只有 1800/1801/LC） |

## 3. agent 侧配置建议

- **persistent=true**：LC 通道（AT/OTA）依赖异步 Notify，且手环对"快速反复连断"耐受差
  （会出现服务发现挂死，见 §4）。空闲轮询的时间片断连模式不适合这台 DUT。
- 一次性命令（WRITE_CHAR/READ_CHAR）会自行申请槽位建连，persistent 只是避免空闲断连。

## 5. 遗留问题

1. **服务发现偶发挂死**：高频连断循环下约半数周期 `discoverServices` 无应答（4s 预算强断）。
   persistent 模式规避；根因待查（疑似手环 ATT 层对快速重连的耐受问题）。
2. **直连无扫描**：agent 按 MAC 直连，不校验对端是否真在广播可连接包。
   后续"扫描选择输入"功能落地时可顺带做连接前探活。
3. REGISTER 重复上报导致的心跳/视图噪音已大幅收敛（84d6fc6），重注册仍发 2~3 条 REGISTER。

## 7. OTA 全流程实测（2026-09-25，PASS）

链路：server 上传 `no_res_ota.zip`（8.6MB）→ `POST /api/files/<id>/transfer` →
server TCP 推帧到 agent → agent LC 通道传输到手环（`300→33bin→330→4480B+CRC32 逐块 310→32→320`）
→ `00AT^OTA_UPDATE` → 手环回 `OTA_UPDATE=OK` 并 `reboot recovery` → 黑窗约 6 分钟
→ 手环自动重开广播 → agent 回连 READY → `AT^SWVER=APP` 回 `SWVER=OK,3.101.042monkey`。

- 传输速率约 **12.5 KB/s**（224B 包 + 4480B 停等 ACK），8.6MB 全程约 11.5 分钟。
- 同版本包未触发 DOWNGRADE 拒绝（FACTEST/Monkey 固件）。
- 加速方向：固件同一套 33x 协议支持 SPP 承载（B319 spplibrary 实证，39600B 块/960B 包），
  SPP UUID `db764ac8-4b08-7f25-aafe-59d03c27bae3`（自定义，非标准 1101）。

## 8. SPP 通道可行性实测（2026-09-25，PASS）

**P67 Monkey 固件开经典蓝牙的 AT 与 B319 时代不同**（实测校准）：

| 步骤 | 命令 | 回包 |
|-|-|-|
| 开经典蓝牙 | `00AT^BT_ENABLE` | `ENABLE_BT=OK` |
| 设扫描模式（3=可发现+可连接；=1 实测连不上） | `00AT^BT_ACCESS_SET=3` | `OK=BT_SCAN, 3` |
| B319 旧指令 `AT^FAC_BT_ACCESS_SET=1` / `AT^REQUEST_SPP_CONNECT` / `AT^BT_AUTO_PAIR` | — | 全部 `unknown cmd`，不存在 |

RFCOMM 实测：自研 UUID + **非加密 socket 3 秒连上、免配对**（`createInsecureRfcommSocketToServiceRecord`），
发 `300` 收 `300`——33x 协议在 SPP 承载上握手通过。SPP 加速通道方案可行，进入开发。

## 11. 导出数据完整性定位与修复（2026-09-26，PASS）

**症状**：agent 导出的文件有 448B（2×224B 包）区段被流中更早位置的包顶替，每次导出位置随机，
但逐块校验全过（固件对自己发出的内容算校验和，顶替段来自同一流所以校验不报错）。
对照实验 blescan 极简直连导同一文件逐字节完美 → 嫌疑锁定 agent 接收管线。

**定位手段**：AndroidGattClient 临时诊断打点（每个 notify 记 seq/len/head/线程名）。
实测 GATT 回调确在多 binder 线程并发分发（Binder:xxxx_1/_2 交替），但诊断版导出
流完全有序、文件逐字节正确——**乱序根源不是回调竞态，而是固件跨 BLE 连接续推的
上次导出残留流混入新会话**（每次残留量不同 → 错乱位置随机）。

**修复**（`02037a5`，4 次连续导出 sha256 全一致验证）：
- 建连后 `drainStaleData` 排放残留流（300ms 静默判定）
- `openExport` 改 `awaitSizeFrame` 扫描定位合法大小帧（'@'+u32BE 总大小且紧随块帧头），跳过残留块帧
- 062 语义修正为拉取式：数据耗尽后再发一次 062 固件才回 `AT^FILE_EXPORT_OVER\0`
- 总大小 512MB / 块长 4480 防御上限

**协议新发现**：本次固件按 **280 字节块**导出（非文档 4480），一块拆两个 224B notify
（MTU 231），块帧头 `@`+u32BE(280)。块长以固件实际行为为准，agent 侧按帧头解析不假定固定块长。

**环境备忘**：Redmi Note 9 Pro 实际为 **Android 12（API 31）**，走 BLUETOOTH_SCAN/CONNECT
运行时权限模型；重装 APK 权限即重置，MIUI 禁止 shell `pm grant`（SecurityException），
必须 UI 手动授权「附近的设备」。权限缺失时 agent 进入 restricted mode（仅上报不操作 BLE），
FILE_EXPORT 报 errorCode=1001。

## 12. SPP 承载导出（2026-09-26，含完整破案链）

实现：`spp/SppByteStream`（RFCOMM 二进制块通道）+ `spp/SppExportOpener`（BLE 前置
BT_ENABLE/BT_ACCESS_SET=3 → RFCOMM 建连）+ `LcExporter` 双承载（同一套 061/062/063
状态机）+ `FileExportManager` 按设备 `transferChannel` 选路（ble/spp/auto，auto 回退 BLE）。

**SPP 与 BLE 导出协议差异（全部真机抓包/固件日志实证）**：
- 同：061 开流（大小帧 '@'+u32BE 总大小）、062 拉块、063 重传、块帧 '@'+u32BE(块长)+数据+4B 大端字节累加和、EOF 再 062 → `AT^FILE_EXPORT_OVER\0`
- 异：**SPP 块长 40960**（BLE 280/4480）；SPP 为 RFCOMM 可靠流，无 BLE notify 丢包/幽灵插入
- B319 bt226 的 `sendMsg` 对 061 追加 `\0`（C 字符串终止符）；P67 实测不带 `\0` 固件也能 dispatch（固件日志 `spp recv` / `file export start` 为证），带上无害
- B319 另有 0620/0621 拉取/重传方言（test_log=false 分支），P67 用 062/063

**破案链（每个坑与根因）**：
1. 扫描器块长上限写死 4480 → SPP 40960 合法帧头被误判垃圾跳过 → 061 假"无响应"。修复：块长上限按承载区分（BLE 4480 / SPP 65536）
2. 长流中段中断：诊断捕获**同步写盘挂在 SPP 读线程** → 手机 RFCOMM 收满流控 → 固件 `facbt spp send failed`（手环日志实证）。修复：诊断写盘改异步队列
3. 速率仅 ~4KB/s：062 拉取节奏每块空等 500ms → 手环 pm_mgr 把链路打 sniff（792ms 间隔）。修复：SPP 模式 QUICK_POLL 压 80ms 保持链路占满（实测 ~38KB/s）
4. 固件跨连接**重播被中止的导出流**（061 即从头重启流），agent 侧 drain + 重播块识别（与上一块字节对比丢弃）
5. server 导出会话被新请求顶替 → 结果错记/帧丢弃。修复：进行中导出 409 拒绝新请求（僵尸会话 2h TTL 允许取代），对齐 agent 单线程串行
6. `transferChannel=auto` 的 BLE 回退会与 SPP 诊断捕获互相截断（共用文件路径）→ 诊断流按会话时间戳分文件

**手环日志自检通道**：`tmp.log`/`crash1.txt` 内 fac 日志记录每次收发的命令与
`file export start`/`facbt spp send failed` 等事件——BLE 导出 tmp.log 即可复盘固件视角，
是定位通道问题的关键手段。

## 13. SPP 目录导出收官（2026-09-26 晚，PASS）

**验收**：export-3af3375c，12 个文件（4.7MB）**160 秒**全部导出（≈29KB/s，BLE 需 ~17 分钟），
errorCode=0；gz 全部 `gzip -t` 通过（参考项；日志目录为活文件，整文件一致性本就不作验收）。

**最终架构**：目录导出 = 一次 LS（一条 SPP 会话仅列举）+ **每文件独立 SPP 会话**单独导。
依据：全天实证"新 SPP 会话 + 直接 061"单文件导出 100% 成功，而"一条会话 LS+多文件"
时固件导出流路由不稳定（061 死信，`FILE_EXPORT_OVER` 实测出现在 BLE 通道——双通道
并存时固件导出任务输出路由不可靠）。

**收官阶段新修 4 项**：
1. **transferChannel 不随 PUT /devices 在线下发**（只写库，agent 仅注册时收全量配置）
   → 一轮目录导出误走 BLE 41 分钟才暴露。规避：改通道后重启 agent App 重注册。
   待办：补运行期下发通道（SET_TRANSFER_CHANNEL 或全量配置推送）。
2. SppExportOpener/SppTransferAdapter 等 AT 应答时**过滤非 AT 行**（BLE LC 通道与
   导出/LS 共用，"F /data/..." LS 条目曾被误读为 BT_ENABLE 应答判拒绝，2001）。
3. server 导出会话进行中拒绝新请求（409，僵尸 2h TTL 允许取代）——顶替曾让
   成功结果被错记/帧丢弃。
4. 目录模式首文件 061 失败整体快速中止（不再 22 文件 × 重试空磨 6 分钟）。

**临时诊断代码已全部移除**（NTF 打点/流捕获/ASCII 旁路），诊断期结论均已固化到
本文档与代码注释。
